# Studio exclusion protocol assessment (issue #5)

Assessment at commit `8d95111`, 2026-11-09. **No protocol has been validated that proves Studio closed and prevents it starting throughout a plugin transaction in normal supported environments.** Keep production write-back disabled. This is an evidence-limited conclusion, not proof that no such mechanism could ever be built. The existing [real-Studio lab](README.md) and [recorded results](evidence/studio_lab.json) are reproducible evidence; no additional Studio run was made for this assessment.

## What participates, and what does not

The vendor supports macOS, Windows and beta Linux, both offline local libraries and optional Premium sync ([desktop guide](https://byok.io/studio/guides/desktop-app), [downloads](https://byok.io/studio/desktop)). The tested app is the **Linux port** of Studio 1.1.3, Electron 44.4.5, with app.asar SHA-256 `25e93b78fb4753f7b47236a91f8907e674c341aab19af271d93c7dd1e04dbcfa`; it is not evidence for the current official Linux build or other platforms.

In that pinned vendor archive, `main.js:23-35` sets `userData` to the `studio-desktop` directory under Electron's app-data path. An unpackaged development run can override it with `STUDIO_USER_DATA_DIR`; the comment says the singleton is per data folder. At `main.js:43-58`, Studio calls Electron's `requestSingleInstanceLock()`, quits if false, and otherwise focuses its window on a second-instance event. These are observations of this build, not a documented BYOK external-writer API. To inspect the same bytes without opening a library, pass the pinned archive to the existing [source probe](../studio_outbox_blocker/probe.py) for a hash check and examine `main.js` using an ASAR reader; the [write-guard lab](lab_studio.py) records the hash independently.

[Electron documents](https://www.electronjs.org/docs/latest/api/app#apprequestsingleinstancelockadditionaldata) a cooperative *application single-instance* API: a second application can notify an existing instance and is expected to quit. It does not document a BYOK library-maintenance lease, that an arbitrary Obsidian process can acquire Studio's identity, or a guarantee spanning all access paths, users and namespaces. A helper Electron application configured to use the same profile is a conceivable research candidate, not an established integration: its acquisition might notify an already-running Studio, and startup by a second instance may notify or focus the helper; failures, helper death, release timing and identity need investigation. Even a success against one profile would not show that every Studio able to access the database uses that same singleton identity. No such helper experiment was performed here. Electron's API is a stronger candidate than fabricating a lock file, but cannot currently authorize writes.

The [recorded lab](evidence/studio_lab.json) shows an actual second Studio instance exited while the first was running; it also shows dead-PID singleton symlinks replaced on launch, including a different-host string. Thus a created symlink is not a cooperative lock. The [Chromium Linux implementation description](https://chromium.googlesource.com/chromium/chromium/+/refs/heads/main/chrome/browser/process_singleton_linux.cc) describes a profile socket, cookie, host and PID with stale-instance handling; it is upstream background, not proof of the exact Chromium revision or behavior of Studio on other systems. Do not fabricate singleton state or signal unrelated processes.

The same lab shows Studio launched during a SQLite exclusive hold and read the committed value after release. After an eight-second hold exceeded Studio's observed busy timeout, the process was alive without a window and no SQLite lock remained. A successful SQLite lock or process scan is therefore not proof of closure. Scans also cannot eliminate the check/start race, and executable names, symlinks, version changes, PID reuse, permissions, hidepid, containers and PID or mount namespaces can defeat identity or visibility. File paths are not identities: aliases, bind mounts, different app-data roots and namespace-relative paths may map differently; conversely a singleton profile and a database must be shown to cover the same access domain. Different users, sessions, machines or an existing process outside the observer's namespace cannot simply be assumed visible or cooperative. The tested jail exercises a shared database inode across namespaces, not every such environment.

## Fail-closed boundary and options

Any future solution needs an explicit vendor-supported maintenance/exclusion contract covering every Studio process that can reach the exact library, already-running activity and new startup, with atomic acquisition held from before the final state checks through commit or rollback. Unknown library/profile mapping, aliases, permissions, versions, user/session/namespace scope, lock loss, crashes and unsupported filesystems must refuse. SQLite transactions and compare-and-swap still protect their own database operations; they do not supply the missing Studio-closed guarantee. SQLite itself says [WAL does not work across hosts on a network filesystem](https://www.sqlite.org/wal.html). Holding a SQLite lock longer is not a substitute, and can strand Studio at startup as observed.

Concrete paths forward:

1. Ask BYOK to expose and document a maintenance lease or supported write API with exclusive acquisition, existing-client quiescence, startup enforcement, identity, crash recovery and version guarantees. Validate it with disposable builds and libraries on each supported platform and across relevant user, profile and namespace boundaries. Closure is only one condition: retain schema, outbox, conflict and sync checks independently.
2. Keep the existing one-way export and let the user transfer edits through Studio's UI. This avoids direct plugin writes; concurrent manual edits and sync conflicts remain the user's responsibility.
3. Continue isolated research on an Electron helper using the real API and a fresh profile, with no access to user processes or networking. Test both acquisition orders, races, crashes, aliases, different profiles, versions and namespace/session/user boundaries, including negative and uncertain cases. Even success on these experiments would need an authorized supported integration and full scope before production use; a launcher controlled only by the plugin cannot govern Studio launched independently.

The documented vendor backup/restore workflow may help users preserve data, but a backup is recovery rather than transaction exclusion. The existing [outbox analysis](../studio_outbox_blocker/README.md) and [migration analysis](../studio_migration_provenance/README.md) describe additional blockers that a closure mechanism alone would not resolve.
